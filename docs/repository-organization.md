# 译伴项目组织与开发约定

更新日期：2026-10-27。本文件记录当前仓库分工、起步来源与开发流程；功能需求仍以根目录需求文档及相关设计草案为依据。

## 1. 本轮依据与范围

用户转述的课堂补充要求包括：使用起步工程并保留首次提交、设置 `master` 与 `develop`、组织多个代码仓库、采用清晰的代码分层；第三方登录为加分项。

本项目据此采用三个实现仓库，并保留既有资料仓库。单人开发使用分支、自查、PR 和验收记录，保留可追溯过程。多仓库与目录分层只是组织基础，功能正确性、权限与可靠性仍须通过后续实现和验收证明。

当前在 Gitee 开发、GitHub 镜像。任务书中的校内 GitLab 按用户安排留到最终提交阶段处理；这项安排不撤销最终交付要求。

## 2. 仓库职责与本机布局

四个仓库分别位于 `~/projects/` 下，彼此同级，独立管理 Git 历史与远程地址。

| 本机目录 | 职责 | 本仓中的内容 |
|---|---|---|
| `~/projects/bilingual-ebook-generator` | 项目资料入口 | 需求、逻辑模型、状态机、接口契约、历史原型与课程记录 |
| `~/projects/yiban-web` | 用户端应用 | 页面、交互、路由、前端状态与 API 适配 |
| `~/projects/yiban-admin` | 独立管理端应用 | 管理员入口、管理页面与 API 适配；首版只读任务和失败元数据 |
| `~/projects/yiban-api` | 共享后端服务 | 账号、角色、属主、上传、解析、翻译、任务、持久化、成果与鉴权下载 |

用户端与管理端共享后端业务规则与接口，真实权限由服务端执行。前端 `src/api/` 是调用适配层，实际业务接口属于 `yiban-api`。后台任务处理器先随后端工程组织，是否拆分部署由异步机制设计决定。

### 代码分层

| 仓库 | 当前工程目录与后续职责 |
|---|---|
| 用户端 | `src/views/` 页面；`src/components/` 公共组件；`src/router/` 路由；`src/stores/` 状态。接口与业务类型按接入批次建立 |
| 管理端 | `src/views/` 页面；`src/api/` 请求与类型；`src/utils/request.ts` 请求封装；公共布局与组件继续复用 |
| 后端 | `api/` 路由；`schemas/` 请求响应；`service/` 业务流程与事务；`repository/` 数据访问；`models/` 数据模型；`core/` 基础设施；`tests/` 对应验证 |

后端 API 调用 Service，Repository 承担数据访问。跨表完成流程由 Service 控制事务，不能照搬模板逐条 Repository 提交。教师学生管理示例、返回码、默认角色和通用 CRUD 不直接作为译伴业务设计。

## 4. 分支与双平台同步

### 三个实现仓库

| 分支 | 用途 | 合入方向 |
|---|---|---|
| `master` | 已验收的稳定批次 | 接收 `develop` 的阶段性 PR |
| `develop` | 开发集成 | 接收功能、修复或文档 PR |
| `feature/*` | 一个可验收的功能批次 | 从 `develop` 创建，向 `develop` 提 PR |
| `fix/*` | 明确问题的修复 | 从 `develop` 创建，向 `develop` 提 PR |
| `docs/*` | 文档与协作规则修订 | 从 `develop` 创建，向 `develop` 提 PR |

相关改动按可验收批次合并。`develop` 的每次文档或小改动无需立即再向 `master` 发起独立 PR；阶段稳定并验收后统一提升。`master` 在 Gitee 形成合并提交时，应及时同步回 `develop`，避免分支积累无关分歧。

### 资料仓库

`bilingual-ebook-generator` 当前保留 `main` 与既有原型历史；本仓文档使用 `docs/* → main`。三个实现仓库的 `master/develop` 规则与本仓分开表述，最终交付时再核对老师对资料仓库分支的具体要求。

### 远程与保护设置

- `origin` 为 Gitee，`github` 为 GitHub；Gitee 是日常 PR 合并入口。
- 合并后将对应分支的同一提交同步到 GitHub；GitHub 保留相同历史。
- 截至本次核对，三个实现仓库的 `master` 均已在两平台启用保护，Gitee 默认分支均为 `master`。
- Gitee 规则保留所有者的推送与合并权限；GitHub 允许正常镜像推送，关闭允许强推与删除的选项。PR 是日常工作约定，不声称配置已完全禁止所有者直推。
- 当前没有 CI 门禁，也不要求单人项目由另一人审批。后续新增自动检查时再调整对应规则。
- 合并前核对工作区、分支、远程差异与验证结果。遇到分歧先分析原因，保留现有工作与提交历史。
