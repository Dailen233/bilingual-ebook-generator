1. 产品定位

面向语言学习者的双语电子书生成产品，核心定位"一键式双语阅读伴侣"（来源：选题原文）。用户上传单语电子书（TXT / EPUB / 文本型 PDF），指定目标语言，系统将原文与译文逐句或逐段对照排版，生成可下载的双语电子书。

产品形态（用户决定 G9，2026-09-24 升级）：从单页面工具升级为有完整用户端与独立管理端的多页面产品。手机端须能完成上传、查看进度、阅读、下载——先规划响应式 Web + 可安装 PWA；原生 Android/iOS App 记为后续独立里程碑，不写成当前已实现（G10）。

本项目首先是一款希望真实可用的产品，课程设计是它当前的开发场景。优先保障：原文与译文对齐可靠、生成的 EPUB/PDF 真正可阅读、失败可恢复或有清楚反馈、长书处理体验、文件与下载链接隐私、后续维护扩展（来源：用户产品导向原则，见 CODEBUDDY.md）。

视觉主方向（用户决定 G12）："现代东方阅读"——暖白纸色、墨蓝、玉石绿、少量暖金，阅读感与现代产品感兼顾。产品结构与流程借鉴 Lulu、Paperturn 的产品介绍结构及双语电子书产品的工作台流程，只借鉴设计方法，不复制素材/内容。

FR-02 正文提取与噪音过滤 【核心】

按文件类型调用对应解析器（选题模块清单：TxtParser / EpubParser / PdfParser），提取正文内容与章节结构；过滤目录、页眉页脚等噪音。PDF 范围限定为结构化较好的文本型 PDF（选题原文限定）。

  • 验收标准（本项目拟定，样本与合格线在测试设计阶段确定）：对受控样本，章节结构完整、正文段落连续，可判定的目录/页眉页脚不混入正文；对仅凭内容无法可靠判断的重复行与结尾文字保守保留，不以"重复"或个别词语误删正文。具体合格指标（章节数一致、噪音行占比、误删率）在测试设计阶段与用户共同确定。
  • 小型受控样本（供验收，本项目拟定；目录与页眉页脚的结构/来源已显式标注）：
  • 输入（TXT，1 本书：目录块 + 正文 + 重复句 + "The end" 开头正文句 + 独立一行 "The end" 结尾）：

    Contents
    Chapter 1 ....... 1
    Chapter 2 ....... 5

    Chapter 1
    The wind blew hard.
    The wind blew hard.         ← 与上句重复；无结构证据证明其为页眉，保守保留
    She waited by the door.
    The end of the road was near.   ← "The end" 为正文成分，不作固定噪音

    Chapter 2
    It was quiet now.
    The end                    ← 独立一行的结尾文字；本样本中属正文，保守保留
  • 预期结果：
  1. 目录块（Contents 标题 + 带"前导点 + 页码"的条目行）被识别为目录并剔除；正文从 Chapter 1 开始。
  2. 章节标题 2 个（Chapter 1 / Chapter 2）保留，章节结构完整。
  3. 重复句 The wind blew hard. 两处均保留（仅凭重复不足以判定为页眉，保守处理）。
  4. The end of the road was near. 保留（"The end" 不是可靠噪音词，可能是正文结尾内容）。
  5. 独立一行的结尾文字 The end 保留（本样本中属正文，不以固定关键词删除）。
  6. 正文段落顺序与原文一致。
  • 页眉页脚处理口径（保守）：仅在存在可判定结构信号时剔除——如 PDF 的页边距/页眉区域、EPUB 的分文件或固定模板、或显式分页标记；纯文本无分页/格式标记时，重复行不默认当页眉删除。
  • 说明：此样本验证"目录结构识别 + 章节结构 + 保守去噪"的确定性行为；真实书籍目录/页眉页脚形式多样，识别准确率与误删率仍待真实样本实测细化，不承诺所有 TXT/EPUB/PDF 噪音都能自动识别。
  • 待验证能力：真实样本下目录/页眉页脚的识别准确率与误删率（不写成既成事实）。

FR-04 分句/分段与原文译文对齐 【核心】

将提取的原文按句子或段落切分为带序号的翻译单元列表，为逐句对照做准备（选题原文：避免整书翻译导致对照混乱）。

  • 验收标准（本项目拟定）：样本书切分后，生成的双语结果中每个原文单元有且仅有一个对应译文单元，无遗漏、无错序；切分粒度与样本的人工计数在约定容差内一致（容差在测试设计阶段确定）。
  • 小型受控样本（供验收，本项目拟定）：
  • 输入（1 段 3 句，英语）：The fog rolled in. She locked the door. Then she waited.
  • 预期切分：3 个带序号翻译单元 —— ①The fog rolled in. ②She locked the door. ③Then she waited.
  • 预期对齐：生成结果中每个序号单元有且仅有一个同序号译文单元，顺序与原文一致（①→①'，②→②'，③→③'），无遗漏、无错序；若第 ② 单元翻译失败，则第 ② 单元保留原文并标记"翻译失败"，①、③ 对齐不受影响。
  • 说明：此样本验证"切分计数 + 一一对齐 + 失败不影响邻位对齐"；真实书籍的切分粒度容差仍待实测细化。

FR-05 第三方翻译 【核心】

接入第三方翻译 API 完成逐单元翻译（具体服务在设计阶段结合语言对支持能力核对后选择，本阶段不锁定）。需处理限流、重试、错误回退：翻译失败的单元保留原文（选题原文，翻译调度模块）。

  • 验收标准（本项目拟定）：模拟个别单元翻译失败时，该单元在结果中保留原文并带"翻译失败"标记，整书任务继续完成；结果页展示失败单元数量。
  • 待验证能力：所选服务对六语各语言对（六语两两共 15 个无方向组合；全部双向为 30 个有方向语言对）的实际支持范围与质量。
  • 关联：翻译服务/模型的选择与偏好配置见 FR-16（v4 原型已含该交互；模型选项有无依据各家官方 API 文档核实）。

FR-06 双语排版生成 【核心】

将原文与译文按对照布局重新组装（选题原文提及"左原右译"、"上下对照"，模块描述提及"对照/交替"），保留原书段落结构，适合移动端阅读（选题原文质量要求）。

FR-07 双语电子书生成与导出 【核心】+【用户 G2】

生成后的双语电子书导出 EPUB 与 PDF 两种格式（用户决定 G2：两者都实现，为本项目目标）。

  • 验收标准（本项目拟定）：处理成功后同时可下载 EPUB 与 PDF 两个文件；EPUB 可在主流电子书阅读器打开、PDF 可在浏览器/PDF 阅读器打开，对照排版与章节结构完整（具体渲染合格标准在测试设计阶段确定）。
  • 待老师确认：原文"导出为 .epub 或 .pdf"的最低验收语义（至少其一 vs 两者都要）——无论确认结果如何，本项目目标均为两者都实现。
  • 待验证能力：两种格式在目标阅读器/浏览器中的渲染质量。

FR-08 下载与分享 【核心】

生成后的双语电子书可通过浏览器直接下载保存（选题原文"微信/浏览器"；本项目暂定响应式 Web 形态，T2）。

  • 验收标准（本项目拟定）：在桌面与移动浏览器中点击下载均获得可用文件；文件内容与服务端生成结果一致。
  • 待定：分享形态（下载链接策略）与是否要求适配微信内浏览器，见第 10 章 P7。
  • 隐私（产品导向原则）：上传文件与下载链接的隐私保护要求列入 NFR-03。

FR-09 处理进度与任务连续性 【可选/进阶】+【用户 P1/G4】

长书籍/一般任务采用后台处理，前端展示进度（选题原文进阶项，如"已翻译 45/200 页"）。用户决定 P1：

  • 处理任务在用户关闭网页后仍可运行；用户回来能查看任务状态与结果；
  • 不等于处理失败后自动从已翻译段落断点续做（断点续做未确认、未承诺）；
  • "阅读位置"是独立需求（FR-13），不得与处理进度混写。
  • 验收标准（本项目拟定）：提交任务后关闭页面，重新打开后任务状态仍可见——处理中（含进度）或已完成（含结果入口），任务不丢失。
  • 待定：异步适用范围（所有书统一异步 vs 短书同步长书异步）与进度计量单位（翻译单元 vs "页"），见第 10 章 P5。具体任务机制（是否用消息队列等）属设计阶段，本阶段不预设。

FR-10 历史记录 【可选/加分】+【用户 G3】

记录用户处理过的书籍，支持列表查看。选题原文给出的字段线索：书名、语言对、生成时间、下载链接。

  • 验收标准（本项目拟定）：成功处理两本书后，个人书库显示两条记录，字段完整（书名、语言对、时间、状态），可点击查看详情/下载入口；记录仅属主可见。
  • 归属：记录归属到登录用户（用户决定 G11，更新原 P3"匿名归属"暂定方案，见第 10 章 P3 变更说明）；依赖 FR-14 的注册/登录与属主校验。

FR-11 重新下载 【可选/加分】+【用户 G3】

从历史记录重新下载已生成的双语电子书。

  • 验收标准（本项目拟定）：对历史记录的任一条已完成记录，可重新下载 EPUB 与 PDF，内容与首次生成一致；原下载链接失效时重新下载仍可用（兜底 E7）。

FR-12 书签 【可选/加分】+【用户 G3】

用户可对书籍中的位置添加书签并再次查看。

  • 范围定位（本项目拟定，待确认）：书签与站内阅读体验绑定，建议随"后续目标"阶段实现，不列入首版必须项（依据 G3"按阶段安排"与 P1 对阅读侧的单独安排）。
  • 验收标准：在所属阶段的设计文档中细化（本阶段不定）。

FR-13 阅读位置 / 继续阅读 【可选/加分】+【用户 P1/G3】

用于将来的站内阅读体验：记录用户在书内的阅读位置，再次打开时从该位置继续。

  • 范围定位（用户决定 P1）：与处理进度是两个不同需求，单独记录和安排，不首版承诺；选题原文"继续阅读上次翻译进度"的歧义（阅读位置 vs 任务进度）已按 P1 澄清为前者，未把两者等同。
  • 验收标准：在所属阶段的设计文档中细化（本阶段不定）。

FR-14 注册、登录与记录归属 【用户 G9/G11】

提供注册/登录；登录后的书籍、任务、下载与阅读记录归属到具体用户（更新原"匿名记录归属"暂定方案，见 P3 变更）。受保护路由与资源按属主校验。

  • 验收标准（本项目拟定）：
  1. 未登录访问工作台/书库/创建任务，被引导到登录/注册。
  2. 注册并登录后，其上传的书籍、任务、下载仅出现在本人书库，他人登录不可见。
  3. 用户 A 直接访问用户 B 的任务/书籍路由，返回无权限（服务端校验），不泄露 B 的数据。
  • 待定：注册字段（邮箱/手机号）、密码策略、是否支持找回密码，见第 10 章 P12。

FR-15 管理端（用户与权限、任务与失败、资源用量、举报/审核、处理记录）【用户 G11】

管理员通过独立入口登录，进入后台，可管理用户与权限、查看任务与失败情况、查看资源用量、处理举报/审核队列、查看处理记录。上传文件默认私有；管理员查看文件内容须满足 FR/4.5 条件并留痕。

  • 验收标准（本项目拟定）：
  1. 普通用户无法通过管理端路由或接口访问管理功能（服务端返回无权限，不只靠前端隐藏菜单）。
  2. 管理员可看到全量任务与失败原因、资源用量统计。
  3. 举报进入审核队列，管理员处置（通过/驳回/屏蔽/删除）后写入操作日志（操作人、时间、对象、原因）。
  4. 管理员在无审核上下文时查看用户私有文件内容被拒绝并记录尝试；在审核上下文中查看则留痕。
  • 边界：不承诺自动识别全部违法或色情内容（见 4.5）；自动化检测仅作辅助候选（见 3.3）。
  • 首个真实可运行里程碑仅含"管理端最小集"（独立登录 + 任务/失败只读查看），完整管理端在 M2 里程碑（见 3.6）。
  • 当前实现状态：用户端无举报提交流程，管理端举报审核页（admin-reviews.html）为「后续审核场景预览」，使用预置示例记录（A101/A102/A103）；不构成已完成的用户举报闭环。真实举报提交、审核队列、处置与通知均在 M2 里程碑。

FR-16 翻译服务选择、可选模型与翻译偏好 【用户确认（原型设计轮，2026-09-25~29；G 编号待登记）】

创建任务时，用户在语言设置之后配置翻译服务与偏好；该配置随任务保存并在任务详情中展示。

  • 翻译服务：集中配置维护、服务可插拔（NFR-04）。示例为有道智云文本翻译与 DeepL 翻译，界面统一标注"原型演示，尚未接入"；本阶段不接真实 API，普通用户页面不收集 API Key（密钥属服务端配置，机制设计阶段确定）。
  • 可选模型：仅当服务官方 API 确实提供模型参数时才显示模型选项，不为每家服务编造模型。依据官方文档：DeepL 翻译 API 提供 model_type 参数（quality_optimized / prefer_quality_optimized / latency_optimized）；有道智云文本翻译 API 无模型选择参数，故不显示模型项。
  • 翻译风格：忠实原文 / 文学表达 / 术语一致，各附一句说明；属本产品偏好演示，不宣称各翻译服务原生支持，不承诺准确率。
  • 任务配置保存与恢复：提交时把服务、模型、风格等非敏感字段随任务保存；任务详情页展示同一份配置，刷新后保持；连续创建多个任务互不干扰；旧任务缺少配置字段时正常兼容显示。
  • 验收标准（本项目拟定；第 1–5 项已在 v4 原型按真实点击流程实测通过，第 6 项待真实实现后验收）：
  1. 切换翻译服务后模型选项联动：选 DeepL 显示 3 个官方 model_type 取值；选有道智云不显示模型选择项。
  2. 修改模型或风格后，提交摘要（语言对 / 服务 / 模型 / 风格）实时更新。
  3. 提交后任务详情展示该配置；刷新页面配置不变。
  4. 同一会话连续创建两本书：第二本可正常进入配置与提交，第一本书仍保留在书库。
  5. 旧任务（无配置字段）打开详情页不报错，配置区按缺省处理。
  6. 真实接入后，按所选服务/模型/风格调用翻译，异常按 E5（失败单元保留原文）处理。
  • 来源说明：用户在 v4 原型迭代中确认（服务名称与"是否显示模型"依据有道智云、DeepL 官方 API 文档核实）；G 编号待登记入 CODEBUDDY.md 结论体系。
